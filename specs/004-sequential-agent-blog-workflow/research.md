# Research: Sequential Multi-Agent Blog Workflow

**Date**: 2026-08-03 | **Feature**: 004-sequential-agent-blog-workflow

## Overview

Technical decisions for the Module 2 "Mastering Sequential Agent Workflows" lab. The lab mandates a Flowise "Simple Sequential Chain" wiring three LLM-chain agents. This plan maps that Flowise design onto the repo's LangGraph conventions to produce a runnable, unit-testable Python implementation plus the lab's documentation deliverables. Decisions below resolve every unknown raised in Technical Context.

---

## Decisions

### Decision 1: Orchestration — Linear `StateGraph` (mirror of Flowise Simple Sequential Chain)

- **Decision**: Implement the chain with LangGraph `StateGraph` over a pydantic `BlogState`, wiring Researcher → Writer → SEO Analyst as three nodes joined by unconditional `add_edge` calls. The graph starts at an entry node holding the raw topic and terminates after the SEO node.
- **Rationale**: This directly mirrors the Flowise "Simple Sequential Chain" the lab requires (the assignment's core deliverable). Using LangGraph keeps the design inspectable/serializable per Constitution I, and is identical in spirit to the previous Module 1/2/3 implementations in this repo. No `ConditionalEdge` is needed because the flow is always linear.
- **Alternatives considered**:
  - A supervisor/hierarchical graph (single controller routing between agents): violates the lab's explicit "linear, one-way" requirement and adds branching the assignment does not want.
  - Parallel fan-out of the three agents: produces unrelated outputs, failing the acceptance scenario that the draft reflects the outline and SEO references the draft.
  - Flowise web-only, no Python: not runnable/headless, not testable under the repo's unittest discipline.

### Decision 2: State Schema — single pydantic `BaseModel` carrying forward pass-through values

- **Decision**: One `BlogState(BaseModel)` with fields `topic`, `outline`, `draft`, `seo_feedback`, `error_records`. Each node reads the previous stage's field and writes its own; downstream only the field(s) it was given.
- **Rationale**: A linear chain only needs forward-propagating immutable values; no `Annotated[list, add_messages]` reducer is required (no nested chat histories). Pydantic gives validation + serialization (spec/constitution prefer pydantic `BaseModel` for structured state).
- **Alternatives considered**:
  - `TypedDict` state: works but provides no runtime validation; constitution prefers pydantic.
  - `Annotated[list, add_messages]` message history: overkill — there is no conversational back-and-forth, only a single pass of three artifacts.

### Decision 3: Concrete / fake LLM routing for deterministic testing

- **Decision**: Nodes call `LLMFactory.create(provider=settings.llm_provider)` for real runs, but each agent node accepts an injectable callable (default `None` → production `LLMFactory`). Tests inject a callable "fake LLM" that returns canned outline/draft/SEO text so the chain is fully deterministic and offline.
- **Rationale**: Satisfies Constitution IV (all LLM via `LLMFactory`) *and* Constitution V (deterministic unittest without network). Injection keeps production path identical to the factory rule while permitting offline CI.
- **Alternatives considered**:
  - Mocking `LLMFactory.create` via `unittest.mock`: possible but less explicit and brittle across test boundaries.
  - Recording-only (always hit real API): slow, nondeterministic, flaky in CI — rejected.

### Decision 4: Observability — manual `time.monotonic()` latency + `loguru`

- **Decision**: Track per-node latency in each agent node with `time.monotonic()` (start/end around the LLM call); log the node name + elapsed time via `loguru`. On exception, append an `ErrorRecord` to `BlogState.error_records` and set `processing_outcome="partial"`. No `@timed_node` decorator.
- **Rationale**: Constitution III requires per-node latency and structured errors. But `@timed_node` assumes a classmethod signature (`args[1]` is state); our nodes are plain functions, so the decorator would misread arguments — the correct call here is manual timing. `loguru` is already configured at package import per repo convention.
- **Alternatives considered**:
  - Applying `@timed_node` anyway: would crash/index the wrong frame for plain functions — rejected.

### Decision 5: Export — markdown-only, three deliverables

- **Decision**: `export.py` produces (a) the Prompt-Engineering document (exact text of the three prompts, each followed by one "how it transforms input → structured output" sentence) and (b) the Communication-Protocol Analysis (150–200 word write-up). No PDF. The Final Workflow Canvas deliverable 1 is the Flowise screenshot, produced manually by the user in Flowise, not generated by code.
- **Rationale**: The lab accepts TXT/MD/DOCX for deliverables 2 and 3; markdown keeps the submission diffable and requires no new dependency. The Flowise canvas is inherently a Web-UI artifact — code cannot generate it. Word-count validation on the analysis is a pure function, easy to unit test.
- **Alternatives considered**:
  - Generating a PDF via `pymupdf`: would be a dependency for no requirement — rejected under Constitution VI.

### Decision 6: No new dependencies

- **Decision**: Reuse the existing internal stack (langgraph, langchain + langchain-openai, pydantic, pydantic-settings, loguru). No new packages added.
- **Rationale**: Constitution VI. Every capability (graph orchestration, LLM calls, config, logging, validation) is already satisfied by the approved stack.
- **Alternatives considered**: `pymupdf` (PDF) — unnecessary; `pytest` (tests) — constitution mandates unittest.
