1. State Schema Design

The LegalDocumentState is a TypedDict with three resilience-oriented sub-structs (ExecutionTracking, ErrorHandling, Compliance) alongside business fields. ExecutionTracking records the current step, an ISO 8601 timestamp, a boolean failed flag, and an ordered processing_history list for reconstructing the execution path. ErrorHandling captures fallback_used, fallback_reason, retry_count, configurable max_retries, and error_logs as a list of ErrorRecord (step, error_type, message, timestamp) — each failure is a structured log entry, not a freeform string. Compliance stores an audit_trail of AuditRecord (step, action, datasource, timestamp) and datasources_used for tracing every external interaction. The processing_outcome field (success/partial/failed) is the single trust signal downstream consumers check.

Business fields (document_id, raw_text, extracted_clauses, validation_results, summary, urgency, complexity) are separated from resilience fields so the operational state does not pollute the tracking state. The timed_node decorator (mirrored from module 1) transparently injects paths_taken and per-node latencies into every node's return dict, providing consistent telemetry without manual instrumentation. The key design choice was making error and compliance records structured TypedDicts rather than plain strings — this enables analysis across documents (e.g., "how many ConnectionError failures this hour?") which plain text would require regex parsing for.

2. Error Handling Plan

Three failure scenarios are handled with distinct detection and fallback strategies:

Scenario A — OCR / Legal Database API Failure: Detection is via try/except catching ConnectionError and TimeoutError in the extract_document node. On the first failure, exponential backoff retries (1s, 2s, 4s) fire up to max_retries (configurable, default 3). Each retry appends an ErrorRecord to error_logs. When retries are exhausted, the node switches to _regex_fallback_extract(), a local pattern-matching function that scans for standard legal clause keywords (payment terms, termination, indemnification, etc.). The fallback output is tagged with fallback_used=true, processing_outcome=partial, and datasources_used includes "regex_fallback" alongside "ocr_api" so auditors can see both what was attempted and what succeeded. The design deliberately avoids LLM-based fallback for the OCR step — regex is cheaper, deterministic, and auditable.

Scenario B — Corrupted / Unreadable Document: Detection is in validate_quality via three checks: string length (empty or whitespace-only fails), UTF-8 decodability, and printable-character ratio (below 50% fails). If validation fails, the conditional edge routes to repair_attempt, which strips non-printable characters and normalizes whitespace. If the repaired content has less than 50% of the original character count, repair is considered failed and processing_outcome is set to failed. If repair succeeds, the document continues through the standard pipeline. Unrecoverable documents route to human_review. The 50% threshold is deliberately conservative — in a legal context, losing more than half the content risks missing a critical clause, so human eyes are required.

Scenario C — Processing Timeout: Complex documents on the complex_path node simulate LLM processing with a time.sleep(0.5). The timed_node decorator captures actual elapsed time per node in the latencies dict. If the system health flag (SIMULATE_SYSTEM_DEGRADED) is set, complex_path falls back to simple regex extraction, sets fallback_used=true and processing_outcome=partial. This prevents a single expensive operation from blocking the pipeline while still producing useful output. The degradation is explicit in the audit trail and datasources_used, ensuring the compliance record shows exactly what processing path was taken.

3. Conditional Routing Logic

The graph has four conditional edges, each making decisions based on state:

Quality routing (after validate_quality): Checks execution_tracking.failed. If true, routes to repair_attempt. Otherwise routes to assess_complexity. This is a binary gate — any quality failure triggers repair before any further processing.

Repair routing (after repair_attempt): Checks execution_tracking.failed again. If repair succeeded, routes to assess_complexity. If repair failed, routes directly to human_review. This prevents corrupted data from entering downstream nodes.

Complexity routing (after assess_complexity): Evaluates four factors. (1) Urgency: if "rush", always routes to simple_path regardless of document complexity — speed over thoroughness. (2) System health: if SIMULATE_SYSTEM_DEGRADED is set, routes to simple_path — degraded systems use cheaper fallbacks. (3) Retry history: if retry_count exceeds max_retries/2, routes to simple_path — repeated failures on complex processing suggest the LLM path is unreliable, so the system downgrades to regex. (4) Document complexity: if complexity is "simple", routes to simple_path; if "complex", routes to complex_path. Factors are evaluated in priority order: urgency overrides everything, then system health, then retry history, then complexity.

Summary routing (after generate_summary): If compliance.processing_outcome is "success", routes to END. For "partial" or "failed", routes to human_review. This is the final quality gate — any degradation or failure detected upstream eventually lands here.

4. Resilience Rationale

The design uses three layered defenses with explicit trade-offs. Retry/backoff is the cheapest and handles transient failures (network hiccups, rate limits) — it adds latency (up to 7s for 3 retries) but costs nothing in fallback complexity and preserves the primary processing path. Graceful degradation (regex fallback for OCR, simple_path fallback for complex_path) keeps the pipeline producing output when services are degraded, but every degraded output is tagged with processing_outcome=partial and fallback_used=true so downstream consumers can calibrate trust. Human escalation is the last resort — only for unrecoverable corruption, retry exhaustion, or degraded final output — preventing humans from becoming a bottleneck.

Compliance is built into every state mutation. The Compliance sub-struct records every action and data source. The ErrorHandling sub-struct preserves the full failure trail. Processing_outcome provides a single field that any downstream consumer can check to determine trust level. Every fallback activation, every retry, and every degradation leaves a structured audit record — the legal firm's compliance team can reconstruct exactly what processing path any document took and why.

The key trade-off is completeness versus safety: the design biases toward transparency over silence. A partial result with fallback_used=true is safer than a fabricated attempt to appear complete. The timed_node decorator ensures telemetry cost is negligible — microseconds per node — and provides per-node latency data that can drive future threshold tuning without additional instrumentation.

5. Reflection — Resilient State Management

The trade-off between completeness, safety, and performance is managed by tiering fallback costs. Cheap retry/backoff handles the common case (transient API failures) without degrading completeness. Moderate-cost regex fallback trades accuracy for availability but tags the output so consumers know the quality is lower. Expensive human escalation fires only when automated paths are genuinely exhausted. This tiering prevents the "best possible" result from costing too much latency or money while ensuring no document silently produces bad results.

Retry/backoff improved real-world reliability the most. In a system dependent on external APIs (OCR, legal databases), transient failures are the majority of real incidents — a 300ms network hiccup resolves itself on retry without any fallback logic needed. The exponential backoff with jitter prevents thundering herd problems. Graceful degradation is useful but dangerous — a regex fallback that silently misses a clause is worse than failing loud. The safeguard is the explicit degradation tagging in state. Human-in-the-loop is the most reliable but must be a laser: routing too broadly creates a bottleneck, routing too narrowly risks missing failures.

Three telemetry signals drive workflow adaptation: fallback activation rate per node (if OCR fallback spikes from 2% to 15%, the OCR service is degrading before customers notice), human review rate (if above 10%, confidence thresholds or fallback quality need tuning), and time-to-human (latency from submission to human assignment — a rising trend indicates retry/backoff is too aggressive). These are derived directly from structured fields in the state schema (error_logs, audit_trail, latencies) without custom instrumentation.
