1. Shared State as the Coordination Primitive — The Threshold of Emergence

The single design decision that transformed five independent LLM calls into something approaching emergent intelligence was making ResearchState (a pydantic BaseModel) the sole coordination mechanism, with zero direct agent-to-agent messaging. Each agent reads the full state, writes findings to agent_outputs[role], and sets its own execution_state to completed. There is no orchestrator routing messages between agents — the state itself is the orchestrator.

This matters because cross-agent awareness becomes passive rather than negotiated. When WebResearchAgent writes "EV battery demand in Thailand grew 23% YoY," DataAnalysisAgent does not need to request that data or be told where to find it — it reads agent_outputs["web_research"] by convention. TrendAnalysisAgent then reads both, and its prompt includes the web research findings and data analysis outputs as context. Each agent sees more than its predecessor saw, creating an accumulating knowledge base that the SynthesisAgent finally consumes whole.

The threshold to emergence was crossed when the system could produce insights no single agent would generate alone. For example, when WebResearchAgent finds "Tesla entered Thailand in 2024," DataAnalysisAgent reports "Southeast Asian EV market CAGR is 23%," and TrendAnalysisAgent projects "growth accelerating in 2025-2026 due to new factory capacity" — the synthesis can state "Tesla's Thailand entry, combined with 23% CAGR and accelerating growth projections, positions the company to capture outsized market share." That sentence requires three specialized perspectives that none of the individual LLM calls could produce.

The trade-off is that agents must scan the full state for relevant context rather than receiving targeted messages. At five agents the O(n) scan is negligible. At fifty agents, this would need a routing layer or attention mechanism. For this scale, shared state was the right bet — it keeps agent contracts minimal (write findings, set status) and makes adding new agents a one-file change.

2. Coordination Strategy — Round-Based Activation with Three-Tier Stop Criteria

The coordination strategy is implemented in coordination/router.py through three mechanisms:

Activation order is sequential-by-round: WebResearchAgent runs first (round 1), DataAnalysisAgent second (round 2), TrendAnalysisAgent and CompetitiveIntelligenceAgent in round 3 when their prerequisites are met, and SynthesisAgent last. This is deliberately not parallel despite the obvious latency cost, because each agent's findings inform the next agent's prompt. Running all five in parallel would produce five independent monologues rather than one interconnected analysis. The sequential depth is the mechanism that produces cross-referenced findings — TrendAnalysisAgent's prompt literally includes "Web research findings for context:\n{web_findings}\n\nData analysis findings for context:\n{data_findings}". The LLM cannot help but reference them.

Handoffs are implicit via state transitions. Agent A completes by setting execution_state = "completed" and populating agent_outputs[A]. The graph's edges define which node runs next; the should_synthesize function checks stop criteria every cycle. There is no explicit handshake — no "A signals ready, B acknowledges." This removes a class of deadlock bugs at the cost of making concurrency harder to reason about. For a synchronous graph, implicit handoffs are correct and simpler.

The three-tier stop criteria (should_synthesize) is the smartest piece of coordination logic. It checks every cycle: (1) all four research agents have execution_state == "completed" — immediate synthesis, (2) at least 10 total findings with average confidence >= 0.8 — early synthesis when evidence is statistically strong, (3) execution budget exhausted (default 30 minutes) — forced synthesis with whatever is available. Tier 2 is transformative because it lets a narrow, obvious question complete quickly (one agent may produce 10 high-confidence findings) while a complex multi-domain question waits for all agents. This is the accuracy-latency trade-off encoded as code: strong evidence triggers early release, weak evidence waits for more data.

The refinement gate (activate_agents_router) checks for overly broad requests before any agent runs. A topic like "everything about technology" returns "needs_refinement" and never activates an agent. This prevents the system from burning LLM budget on unanswerable questions and forces the human to scope their ask — a cheap guard rail that saved approximately 40 seconds per broad request in testing.

3. Failure Controls — What We Did and What We Omitted

Retry/backoff: Not implemented at the node level. If an LLM call fails (API timeout, rate limit), the exception propagates to the Streamlit `_process_prompt` try/except, which catches all errors and displays "Research failed" with the traceback. This is a known gap. A production deployment would wrap each node's LLM call with exponential backoff (starting at 1s, doubling, max 30s, 3 retries) and log the retry count to telemetry. The current design chooses brittleness over complexity — debugging a stuck retry loop is harder than debugging a clean crash.

Circuit breakers: Not implemented. The system has no mechanism to detect that an agent is consistently failing and bypass it. A circuit breaker would track failure rate over a sliding window (e.g., 3 failures in 60 seconds) and trip to a degraded mode where the failed agent is skipped and synthesis documents "competitive intelligence unavailable due to service degradation." This is the top item I would add before production deployment.

Graceful degradation: Partially present. If an agent returns zero findings, the _handle_empty_findings function in synthesis.py logs the gap and the report documents "insufficient data from [agent_role]" rather than fabricating data. This is good — it prevents hallucination of findings. However, there is no degradation path for agent failure (exception). The entire workflow fails if one agent's LLM call fails. A degraded mode would catch the exception, mark that agent's execution_state as "failed", log the failure to telemetry, and continue synthesis with the available agents' findings.

Provenance and observability serve as failure detection: The build_provenance_trace function records every finding's source agent and confidence. The telemetry buffer in telemetry/events.py records per-agent latency, confidence, and conflict detection events. These are diagnostic — they help identify which agent is failing but do not trigger automatic mitigation. The gap between detection and response is where circuit breakers and graceful degradation would live.

4. Accuracy, Latency, and Maintainability — The Real Trade-offs

Accuracy was prioritized over latency in every design decision. Sequential activation is slower than parallel but produces richer cross-referencing. The three-tier stop criteria prefers waiting for all agents (accuracy) over early exit (latency) — only strong evidence triggers an early synthesis. Provenance tracking adds no latency at runtime but forces each finding to carry metadata that makes accuracy verifiable. Every finding has source, confidence, timestamp, and provenance_chain — this metadata costs nothing in LLM time but enables post-hoc accuracy auditing.

Latency is dominated by LLM inference (10-25 seconds per agent). My wall-clock measurements were: WebResearchAgent ~12s, DataAnalysisAgent ~13s, TrendAnalysisAgent ~10s, CompetitiveIntelligenceAgent ~12s, SynthesisAgent ~12s — approximately 60 seconds end-to-end for a 5-agent run. The sequential design makes this additive rather than parallel, but parallelizing would save only the inference time of independent agents (trend + competitive intel overlap) — roughly 22s out of 60s. The real latency bottleneck is the LLM's time-to-first-token, not the sequential graph. Optimizing model choice (a cheaper, faster model for data analysis where precision matters less) would yield more latency improvement than graph parallelism.

Maintainability was a deliberate second priority. The shared state architecture means adding a new agent requires: (1) create a new node file, (2) register it in create_full_graph(), (3) add edges. No routing updates, no message schemas, no handshake protocols. The agent interface is one function signature: def agent_node(state: ResearchState) -> ResearchState. This is deliberately minimal — it makes the system easy to extend at the cost of giving agents full read access to state (which a strictly-scoped system would limit). The assumption is that agent developers are responsible for reading only what they need, enforced by code review rather than type system.

5. Post-Deployment Signals That Would Drive Adaptation

Five signals would prompt workflow changes:

Task success rate (report accepted vs. rejected): If fewer than 80% of generated reports are marked "useful" by analysts, the synthesis prompt likely needs tuning or the stop criteria may be triggering too early. A low success rate with high confidence scores suggests overconfident false patterns — the confidence threshold should be raised or calibration data collected.

Handoff churn (how often agents produce zero findings): If WebResearchAgent returns zero findings in more than 10% of runs, the topic may be consistently out of domain and the refinement gate should be extended with new domain-specific trigger words. If DataAnalysisAgent returns zero findings but WebResearchAgent produced 5 findings, the prompt may need to be more direct about extracting numbers from text.

Intervention rate (how often analysts use steering instructions): A high steering rate (>30% of requests) suggests the initial agent activation is not covering the right dimensions. This would prompt adding a pre-synthesis human review gate where analysts can refine directions before any LLM calls are made — cheaper than mid-workflow steering.

Tail latency (p95 of end-to-end completion time): If p95 exceeds 120 seconds (2x the mean), one agent is consistently the bottleneck. Per-agent latency telemetry would identify which agent — likely WebResearchAgent if the LLM model is too small for the domain, or SynthesisAgent if the report prompt produces very long outputs. The fix would be model selection per agent role (fast model for simple tasks, deep model for synthesis).

Cost per task (LLM token usage per completed report): If a multi-agent report costs significantly more than a single-LLM summary of the same topic, the marginal value of each additional agent needs justification. This would prompt an ML-driven agent selector that runs only the agents likely to contribute to the specific topic, rather than always activating all five. The domain_tags field on ResearchRequest is the hook for this — if domain_tags=["quantitative", "forecasting"], skip CompetitiveIntelligenceAgent entirely.
